How this demonstration works

      
This page is a working copy of SynthID-Text, the text watermark Google DeepMind published in Nature in 2024 and released as open source. A language model writes text that looks completely normal, but the exact words it chose carry a hidden statistical signature. Anyone holding the secret key can check for that signature. Anyone without it sees ordinary text.

      
Everything on the Demo tab runs on this machine. Nothing is sent to an outside service.

1. The big picture

      

        
Secret key random numbers
→
        
g-valuesa pseudo-random bit per (recent tokens, candidate, key number)
→
        
Tournamentnudges each word choice toward candidates with 1-bits
→
        
Watermarked textreads normally
→
        
Detectorrecomputes the bits from the text + key and checks whether too many are 1

      

      
A language model writes one token (a word or piece of a word) at a time. At each step it has a probability for every possible next token, and normally it simply samples from those. The watermark changes only that sampling step. It slightly prefers candidates that the secret key happens to score as "1", without changing which candidates are plausible. The model's knowledge, the prompt and the meaning are untouched.

      
Because every preference is tiny and pseudo-random, a single word proves nothing. Over a hundred or more tokens, though, the text carries far more 1s than chance would give, and that is what the detector measures.


      
2. Tokens and n-grams

      
The model () splits text into tokens using its tokenizer. "lighthouse" might be one token, while "Mara's" might be Mara's. The watermark works on tokens, not words or ideas, which is why the heatmap sometimes colors part of a word.

      
An n-gram is a run of n consecutive tokens. This demo uses n = : each token is judged together with the  tokens before it. That short run is the only context the watermark ever looks at. Change any one of those tokens and the watermark for that position is reshuffled.


      
3. The secret key

      
The key is just a list of  whole numbers, one per tournament layer (the "depth"; Google's paper also uses 30). You can see this demo's key on the "Generator & key" tab.

      
    
        
  • How it was made. scripts/make_keys.py drew each number with Python's secrets.randbelow(231 − 1). That is the operating system's cryptographically secure random generator, so the numbers can't be guessed or reproduced. They were saved once to data/keys.json on the server. The script refuses to overwrite an existing key, because a new key makes every earlier watermark undetectable.
    • 
        
  • The "Random key" button makes a throwaway key the same way, in your browser (crypto.getRandomValues, 31-bit numbers). It is never saved.
    • 
        
  • What is not secret. The method, the code, the n-gram length, and a lookup table of  random bits (generated from the public seed ) are all public. Security rests on the key alone, as with a password.
    • 
        
  • Why it must stay private. With the key, anyone can detect the watermark, and forge it: they can make any text, even text a human wrote, look watermarked by choosing words the key favors. Without the key, the bits look like coin flips and nobody can detect, remove on purpose, or fake the watermark.
    • 
      


      
4. g-values: the key's coin flips

      
A g-value is a single bit (0 or 1) that the key assigns to a token in its context. For a candidate token x that follows the tokens c1…c, and for key number i (out of ):

      
    
        
  1. Start with h = 1 and mix in each token id of (c1, …, x) in turn: h = (h + token) × 6364136223846793005 + 1, wrapping around at 64 bits. This is a linear-congruential hash.
    2. 
        
  2. Mix in the key number the same way: hi = (h + keyi) × 6364136223846793005 + 1.
    3. 
        
  3. Look up bit number hi mod  in the public table of random bits. That bit is gi(x).
    4. 
      

      
So every candidate gets  bits, one per key number. You can see them as the strips of little squares in the tournament explorer. The bits look random, but they are deterministic: the same context, candidate and key always give the same bits. That is why the detector can recompute them later from nothing but the text and the key.

      
For any text that was not written with this key, each g-value behaves like a fair coin flip, with a 50% chance of being 1. That includes human writing, other AI models, and this model with the watermark off. This baseline of 0.50 is what the detector compares against.


      
5. Tournament sampling: how the watermark gets in

      
At each step the model proposes candidates with probabilities (after temperature  and keeping the top ). The watermark then runs a tournament with one round per key number:

      
    
        
  • Imagine drawing two candidates from the model's distribution. The one whose g-value for this round is 1 wins. On a tie, a coin decides. Winners advance to the next round, which uses the next key number, and so on for  rounds.
    • 
        
  • The code does this exactly, in closed form. In round i each candidate's probability is multiplied by 1 + gi(x) − E[gi], where E[gi] is the probability-weighted average g-value of all candidates. Candidates with a 1 gain, candidates with a 0 lose, and the total stays 100%.
    • 
        
  • The final token is then sampled from the reshaped probabilities. In the tournament explorer, the gray bars are the model's own probabilities and the red bars are after the tournament.
    • 
      

      
Why the text still reads well. The tournament only reweights candidates the model already considered plausible. Averaged over all possible keys, the output distribution is exactly the model's own (the paper calls this non-distortionary). For one fixed key, it leans toward that key's favorites.

      
Why entropy matters. If the model is nearly certain (say "Statue of" → "Liberty"), there is no choice to steer, and that token carries almost no watermark. Creative writing has many plausible choices per step, so it watermarks well. Higher temperature means more choice and a stronger watermark. Facts, lists and code are much harder to watermark.

      
Two special cases. The first  tokens have no full context yet, so the detector does not score them. And if the same -token context already appeared earlier in the text, the watermark is skipped there (the explorer says so). Otherwise repeated phrases would bias the count. The detector skips those positions too.


      
6. Detection and the z-score

      
The detector never runs the language model. It only needs the tokenizer and the key, so a check takes a few milliseconds:

      
    
        
  1. Split the pasted text into tokens with the same tokenizer.
    2. 
        
  2. For every token after the first , compute its  g-values from its own n-gram, exactly as in section 4. Skip positions whose context repeats.
    3. 
        
  3. Average each token's bits into one score with weights that fall from 10 (round 1) to 1 (round ). Early rounds get more weight because they carry more of the signal: once the first rounds have narrowed the field, later rounds have little choice left to steer. This is the paper's "weighted mean" detector. The token score shown in the heatmap is this weighted average.
    4. 
        
  4. Under the "not watermarked" hypothesis every bit is a fair coin, so the average of all token scores should be 0.50, with a known spread. The z-score measures how many standard deviations above 0.50 the text lands:
          
    z = Σt (st − 0.5) · Σw ⁄ (0.5 · ‖w‖ · √N)
    
          where st is token t's score, w the weights and N the number of scored tokens.
    5. 
        
  5. The p-value is the chance that unwatermarked text would score at least this high (one-sided normal tail).
    6. 
      

      

        
z-scoreVerdictMeaning

        
          
≥ 4Watermark detectedp < 0.00003: about 1 false alarm in 30,000 human texts

          
2 – 4Weak signalsuggestive, not conclusive; typical of lightly edited text

          
< 2No watermarkconsistent with chance

          
—Too shortfewer than 20 scorable tokens

        
      

      
Why length matters. Each token adds only a little evidence, but the evidence adds up. For the same per-token strength, z grows with the square root of the number of tokens, so 4× the text gives about 2× the z-score. A 10-word text can't be judged; 150 words of untouched watermarked text typically scores 13 to 17.

8. What weakens or breaks the watermark

      
    
        
  • Editing. Every changed token changes the n-grams it belongs to (here, up to  of them). A few edits lower the score; heavy editing removes it.
    • 
        
  • Paraphrasing and translation. Rewriting in your own words, or with another model, keeps the meaning but replaces nearly every n-gram, and the watermark goes with them. This is the main limitation of every text watermark, and the key lesson of this demo.
    • 
        
  • Short or predictable text. Too few tokens, or too few real choices per token, means too little evidence.
    • 
        
  • n-gram length trade-off. A longer context (Google's default is 5) makes the key harder to infer from text, but each edit then destroys more positions. This demo uses  so that light edits leave some signal behind.
    • 
        
  • It is not an "AI detector". It only recognizes text made with this key. Text from any other model, or this model with the watermark off, scores like human writing.
    • 
        
  • Key leaks. Anyone with the key can detect, and also forge, the watermark. That is why this demo showing its key is the exception.
    • 
      


      
9. This demo's setup

      
    
        
  • Model: , running on this DGX Spark's GPU. Watermarking uses the SynthID-Text implementation in Hugging Face transformers.
    • 
        
  • Sampling: temperature  and top-k  by default (adjustable). The model's own top-p and repetition penalty are turned off, so these sliders are the only sampling settings in play.
    • 
        
  • Prompt and length: by default the model is asked to retell the story in its own words in about N words (default ), condensing or expanding as needed. The instructions come from data/prompt.txt and can be edited for each generation in the "System message" box; the prompt never contains the watermark, which is applied only while sampling. Whatever the prompt says, generation stops at the first sentence end once N words are reached.
    • 
        
  • Watermark settings:  key numbers, n-gram length , a -entry bit table (seed ), and repeated-context memory of  steps.
    • 
        
  • A fix this demo needed: the stock library builds its bit table with a different random generator on a GPU than on a CPU, so text watermarked on the GPU was invisible to a CPU detector. This demo always builds the table on the CPU, so both sides agree.
    • 
        
  • Compared with Google's production system: the algorithm is the same one used for Gemini, but Gemini uses its own keys and its own hashing, so this detector can't check Gemini output (and vice versa). Google also offers a trained, Bayesian detector; this demo uses the simpler weighted-mean test described in the paper.
    • 
      


      
10. Suggested lesson flow

      
    
        
  1. Detector only. Paste a watermarked paraphrase: detected with a large z-score. Paste the human story: no watermark.
    2. 
        
  2. Light edit. Change 5 to 10 words and watch the live score fall a little. Which words on the "Most influential words" chart did you change?
    3. 
        
  3. Heavy edit, then own words. Reorder and replace; then rewrite from memory. The watermark fades and is gone. Discuss: the watermark lives in exact token sequences, not in meaning.
    4. 
        
  4. Under the hood. Open the "Generator & key" tab. Step through the tournament explorer. Try a random key on watermarked text, and then change one key number.
    5. 
        
  5. Discussion. What is watermarking good for (catching casual copy-paste, labeling content at scale) and what can't it do (stop a determined paraphraser, detect other models)? Who should hold the keys?
